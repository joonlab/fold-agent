## 재계획(replan) 설계안과 오프라인 재생 실험 결과

**결론:** 막힌 4개 실행을 재생해 보니 5개 모델 조합 모두 「같은 동작 반복 중단 → 다른 경로 제안」을 해냈습니다. 007 이 16번 왕복한 원인은 모델 능력이 아니라 루프에 「한 발 물러서는 시점」이 없던 구조입니다. 추천 모델은 **gpt-6-sol(추론 강도 지정 없음)** 입니다. 조건이 두 가지 있습니다. 도구 설명을 자르지 않고 전부 넣을 것, 그리고 실패한 동작을 다시 제안하면 코드가 걸러낼 것.

저장소 파일은 고치지 않았습니다. adb 는 `settings get` 한 번만 썼는데, `stay_on_while_plugged_in` 은 **지금 이미 7** 입니다.

### 1. 설계

**언제 부르나 (execute() 끝에서 `replanReason` 을 세우고, run() 이 다음 llm.chat 전에 확인)**
- **T1 왕복 감시:** Agent.kt:564 의 왕복 감시가 n≥3 일 때(지금은 경고 문구만 붙임) 재계획한다. n≥5 에서 멈추는 동작은 그대로 둔다.
- **T2 같은 동작 무효:** `repeatCount ≥ WARN_REPEATS(3)` 일 때.
- **T3 재방문 (신규):** 최근 3개 도구 결과가 모두 「이미 본 화면」(화면 전문 해시가 같음)일 때. 007 은 5단계, 지도 사례(nmap_card)는 9단계, 노트 입력 사례(notes_type)는 8단계에서 걸린다.
- **T4 실패 연속:** `failStreak ≥ 2` 일 때.
- **T5 (선택) 점검:** 15단계째에 아직 재계획한 적이 없으면 한 번.
- 노트 검색 사례(notes_search, 검색어만 바꾼 검색 반복)는 화면 글자가 달라 T1~T3 에 안 걸린다. 구조 해시(글자를 뺀 해시)를 쓰는 T6 이 필요한데, 목록 스크롤에서 잘못 걸릴 수 있어 보류한다.

**횟수 상한:** 한 실행에 **최대 2번**. 세 번째 트리거가 오면 `stuck` 으로 멈추고, 재계획의 `user_message` 가 있으면 그것을 사용자에게 전한다. 재계획 직후에는 `actionHistory`·`repeatKey`·`repeatCount` 를 비워 감시가 곧바로 멈춤을 내지 않게 한다.

**어떤 형태로 부르나:** 메인 대화와 **따로** 부르고, 도구 없이 JSON 만 받는다(변형 A).
- `LlmClient` 에 `chatJson(messages, model, effort?)` 를 추가한다. timeout 은 30초이고, 실패하면 코드가 만든 기본 안내로 대신한다.
- 대화 전체를 넣고 `tool_choice:none` 으로 부르는 방식(변형 B)도 007·notes_type 에서 4회 시험했다. 질은 비슷했지만 없는 도구 이름(「화면 시각 확인」)과 빈 인자가 나왔고, 캐시 적중은 0이었다. 그래서 A 를 권한다.

**무엇을 넣나 (코드가 만드는 요약, 3.5~5.3k 토큰):**
- 요청
- 같은 세션 이전 턴의 요청→결과 (최근 3개)
- 재계획을 부른 이유
- **도구 전체 설명과 인자 설명 (자르지 않음)**
- 행동 기록: 한 줄에 `단계. 도구(인자) → 결과 첫 줄 [변화/변화 없음] · 결과 화면 한 줄 요약`. 이미 본 화면은 「단계 N 과 같은 화면(다시 봄)」으로 표시한다. 이 한 줄 요약이 ② 「본 화면 기억」의 원형이다.
- 코드가 뽑은 「이미 실패한 동작」 목록 (변화 없음 2회 이상, 재방문)
- 이전 재계획 요약
- [메모]
- 그 앱의 [앱 요령]
- 현재 화면 전문

**받은 뒤 코드가 하는 일**
- `first_action` 이 도구 목록에 없거나, 「이미 실패한 동작」과 같은 키이면 버린다. trace 에 `first_action_rejected` 로 남긴다.
- 결과를 user 메시지로 넣는다. SCREEN_MARK 가 없으므로 이전 화면을 자를 때도 살아남아 기억 역할을 한다.
  ```
  [재계획 1/2 — 이유: …]
  지금까지: {observed}
  가설: ① {claim} → 확인: {check} ② …
  다음 전략: {summary}
  첫 행동 제안(참고 — 인자는 지금 화면과 도구 설명대로): {tool}({args})
  하지 말 것: {avoid…}
  ```
- `give_up=true` 이면 「[재계획] 남은 방법이 없다 — finish(success=false)로 다음 취지로 말하라: {user_message}」를 넣는다. finish 는 메인 모델이 하게 해서 조건 체크를 그대로 거친다.
- trace 에 `replan` 이벤트를 남긴다: step, reason, model, ms, usage, parsed, rejected.
- 재계획이 10~20초 걸리므로 상태에 「🧭 다시 생각하는 중…」을 띄운다.

**재계획 시스템 프롬프트 전문** (실험에 쓴 것 그대로):
```
너는 안드로이드 폰 조작 에이전트의 「재계획자」다. 실행자는 매 턴 도구 하나씩 누르다가 막혔다. 너는 도구를 누르지 않는다 — 한 발 물러나 지금까지의 기록을 읽고, 무엇을 알게 됐는지 정리하고, 가설을 세워, 실행자가 따를 다음 전략 하나를 정한다.
개발자가 로그를 보고 추론하듯 한다:
1. 관찰: 어느 화면에서 무엇을 확인했고, 무엇이 「없었는지」를 사실로 적는다. 이미 본 화면·이미 해 본 동작을 빠짐없이 센다.
2. 막힌 이유: 같은 동작·같은 화면을 반복하는 이유를 한 줄로.
3. 가설 2~3개: 서로 다른 설명(예: 항목이 아직 안 본 곳에 있다 / 이 기기엔 그 항목이 없다 / 동작은 됐는데 화면 목록이 늦게 갱신된다 / 누른 요소가 틀렸다). 각 가설마다 그것을 「한두 동작으로」 확인하거나 반증할 방법(도구 이름과 인자)을 적는다. 이미 해 본 확인은 다시 제안하지 않는다.
4. 다음 전략 하나: 같은 경로를 되풀이하지 말고 다른 경로·다른 도구(전용 도구·설정 검색·딥링크·look 으로 눈으로 확인 등)를 쓴다. 전용 도구가 있으면 화면 조작보다 우선한다. 첫 행동은 도구 목록에 있는 것만.
5. 포기 판단: 남은 방법이 없거나, 확인 결과 기기에 그 기능이 없거나, 되돌릴 수 없는 동작·비밀번호가 필요하면 give_up=true 로 하고 사용자에게 할 말(무엇을 확인했고 왜 못 하는지, 대안)을 적는다. 거짓 성공은 금지다.
규칙: 되돌릴 수 없는 동작(발송·결제·삭제)을 새로 제안하지 않는다(요청에 이미 있던 것은 예외이되 실행자가 확인 게이트를 거친다). 요청 범위를 넓히지 않는다.
반드시 JSON 객체 하나로만 답한다(설명 문장·코드펜스 금지):
{"observed":"2~4문장","stuck_reason":"한 줄","hypotheses":[{"claim":"…","check":"확인 방법(도구+인자)","likelihood":"high|mid|low"}],"strategy":{"summary":"한 줄","first_action":{"tool":"도구 이름","args":{}},"avoid":["다시 하지 말 것"]},"give_up":false,"user_message":""}
```
실험 결과를 반영해 코드에 두 가지를 더 넣을 것을 권합니다. 「이미 실패한 동작: …(다시 제안 금지)」 줄을 입력에 넣는 것, 그리고 이전 재계획이 있으면 「이전 재계획: {summary} → 결과: …, 같은 전략 금지」를 넣는 것.

재생 지점(이 단계의 도구 결과까지 본 상태에서 재계획):

|---|---|---|---|
| 007 | 20260926-232447-007 (cancel, 16단계) | 5단계 | T3 |
| notes_type | 20260926-173214-564 (stuck, 같은 type_text 반복) | 8단계 | T1·T2 |
| nmap_card | 20260926-211214-816 (failed, 21단계, 네이버 지도 카드) | 9단계 | T3 |
| notes_search | 20260926-222849-371 (failed, 21단계, 검색어만 바꿔 반복) | 20단계 | T6 에 해당, 지금 감시로는 안 걸림 |

채점 기준은 네 가지이고, 네 가지를 모두 지키면 통과입니다.
- **A:** 이미 실패한 동작이나 이미 본 화면을 다시 제안하지 않는다.
- **B:** 핵심 진단이 맞다.
- **C:** 첫 행동의 도구와 인자가 유효하다.
- **D:** 안전하고 정직하다(발송·삭제를 새로 제안하지 않고 거짓 성공이 없다).

사례별로 보면 이렇습니다.
- **007:** 10회 모두 「스크롤 왕복 중단 → 설정 검색」을 제안했습니다. 첫 행동은 상위 메뉴 tap 이거나 `open_settings(SETTINGS)` 입니다. 「이 기기엔 없다」 가설도 대부분 넣었지만, 이 시점에서 포기한 경우는 0회였는데 검색이 아직 남아 있으니 적절합니다.
- **notes_type:** 전부 같은 입력 반복을 멈췄고, look 으로 중복부터 확인하거나 write_note 로 넘어갔습니다.
- **nmap_card:** look 으로 확인하거나 결과 시트를 swipe 로 펼쳤습니다.
- **notes_search:** 검색어를 더 바꾸지 않고 필터나 목록을 확인했습니다. 다른 노트를 삭제하자는 제안은 0회였습니다.

**2차: 도구 설명과 인자 설명 전체를 넣은 입력** (gpt-5.6-sol·gpt-6-sol, 각 10회)
- **gpt-6-sol: 10/10 통과.** 2회는 「write_note 는 갤러리 사진을 지정할 수 없다」고 스스로 제약을 짚었습니다. 지연 중앙값은 16.5초지만 **66초, 30초 튐**이 있었습니다.
- **gpt-5.6-sol: 8/10 통과.** notes_type 에서 2회, 이미 두 번 「변화 없음」이 난 `type_text(index 9)` 를 다시 첫 행동으로 냈습니다(A 실패). 지연 중앙값 15.7초, 최대 19.7초.
- 1차의 인자 날조는 도구 설명을 자른 탓이었습니다. 자르지 않자 사라졌습니다.

**3차: 출력을 짧게 한 프롬프트** (순차 호출, 각 4회)
- 지연은 13~15초로 거의 줄지 않았습니다.
- gpt-5.6-sol 은 지도 사례에서 **실패한 tap(14) 를 다시** 제안했습니다. 줄여서 얻는 이득이 없으므로 권하지 않습니다.

**4차: 설정 도구가 목록에 있다고 가정하고 007 재계획** (`settings` get/put, 허용 목록, put 은 확인 후 실행 / 6회)
- 6/6 모두 화면 탐색을 멈추고 settings 도구를 골랐습니다.
- gpt-6-sol 은 2/2 **get 먼저**, gpt-5.6-sol 은 기본·high 모두 4/4 **put 먼저**(값 7) 였습니다.
- 실제 값이 이미 7이라 get 먼저가 맞습니다. 그래서 도구 쪽에서 put 이 먼저 값을 읽고, 이미 같으면 확인 게이트 없이 「이미 켜짐」을 돌려주게 하길 권합니다.

### 3. 추천 모델·강도

- **gpt-6-sol, reasoning_effort 는 보내지 않음.** 실패한 동작을 다시 제안한 비율이 0/22(모든 차수 합계)로, gpt-5.6-sol 의 3/22 보다 낫습니다. 도구 제약도 더 잘 읽습니다.
- **대비책:** 30초가 넘으면 gpt-5.6-sol 로 한 번 더 부르고, 그것도 안 되면 코드가 만든 기본 안내로 대신합니다. 모델 이름은 `Prefs.replanModel` 로 바꿀 수 있게 둡니다.
- **high 는 쓰지 않습니다.** gpt-5.6-sol high 는 지연이 2.3배인데 질이 같았고, gpt-6-sol 은 high 를 줘도 추론 토큰이 늘지 않아 프록시가 무시하는 것으로 보입니다.
- 실패한 동작을 걸러내는 코드 검증이 있으면 gpt-5.6-sol 로도 실사용에 충분합니다.
- **표본이 조합당 2~10회로 작습니다.** ④ 평가 세트에서 다시 확인해야 합니다.

### 4. 비용 추정

프록시가 OAuth 구독이라 호출당 과금은 없습니다. API 단가를 확인하지 않아 금액은 적지 않고 토큰으로만 비교합니다.

- **재계획 1회:** 입력 약 5.3k(전체 도구 설명 포함) + 출력 약 0.7k 토큰, 13~20초.
- **메인 루프:** 007 은 LLM 17회에 입력 113k 토큰을 썼고, 한 단계 중앙값은 3.0초였습니다. 그러니 재계획 1회는 메인 한 단계와 토큰이 비슷하고 시간은 5배쯤 듭니다.
- **007 에 적용했다면:** 5단계에서 재계획하고 설정 검색 3~4단계 뒤 finish(또는 두 번째 재계획에서 포기)하면 LLM 약 10회, 입력 약 60k 토큰, 약 50초입니다. **토큰은 약 45%, 시간은 약 35% 줄어듭니다.** 한 실행에 2회까지 불러도 추가분은 약 11k 토큰입니다.

### 5. 시험하지 못한 것 (④ 평가 세트에 넣을 것)

- **포기 판단:** 설정 검색으로도 「화면 켜짐 유지」가 안 나왔을 때 두 번째 재계획이 `give_up` 과 대안 안내를 내는지. One UI 9 에는 그 항목이 없다는 override 가 이미 있습니다.
- **감지 규칙:** notes_search 형태를 잡는 T6(구조 해시) 을 붙였을 때 잘못 걸리는 비율.
